## 2. 项目要解决什么

项目要从监管处罚材料出发，构造可审计的 `question + Gold SQL + 业务事件 + 数据`，并在一个持续追加的正式 EAST 数据库上通过 SQL 回归。每一个正式交付都必须能回答：

- 处罚中的不可丢失事实是什么，外部证据又是什么；
- 这些事实为何能被 EAST 表、字段和关联观察到；
- Gold SQL、业务事件、候选数据、ORM 和回归结果之间如何一一追溯；
- 所有使用的约束资产来自何处、哪个版本、是否已发布；
- 失败发生在事实、映射、查询规格、question-SQL、数据、ORM 还是铺底状态。

正式库只能有一个。各批次在同一正式数据库中追加，不得将多个独立 SQLite 文件物理合并成“正式库”。

## 3. 全局原则与硬边界

1. **先共识、后实现。** 架构、包名和 Agent 名已确定时，不得自行改名或扩展流程职责。
2. **原始 EAST 材料是事实源。** LLM、EAST 模型和外部资料只做解释、映射、候选或派生关系；不得伪装成监管原文。
3. **LLM 负责受控思考，硬代码负责边界与闸门。** LLM 输出必须满足固定 Schema、固定码值、来源引用校验和版本记录；不确定规则进入人工审核，不能硬猜。
4. **候选不等于发布。** LLM 不可直接写正式库，也不可自行批准 question-SQL、数据或 ORM。所有正式路径均需经过相应的预审、双审、硬编码验证和回归。
5. **242 与 252 只校验。** 单字段、表内多字段、跨表多字段验证模块只接收产物并返回 `通过/不通过 + 违反约束`，绝不生成数据或 ORM。对象—明细—状态只作为跨表引用与操作顺序语义，不存在独立运行期模块。
6. **Foundation 铺底不是业务事件。** 它不构造操作闭包、不走 ORM；经验证后由 260 形成冻结的、带参数的完整 INSERT SQL 批次，再由固定发布代码执行。
7. **包不可覆盖。** 所有产物均有 `artifact_id + version + content_hash`，修复会产生新版本；引用的是不可变产物身份，不是文件路径。
8. **默认最多重试 3 次。** 同一阶段超过 3 次仍不能修复时，停止自动循环并进入人工审核。
9. **无通用错误包。** 每个阶段使用自己的审核/验证/回归报告，错误码与具体证据跟随相应包。

## 4. 总体流程

```text
监管处罚来源
  -> 010 总体调度
  -> 110 question-SQL 阶段调度
  -> 120 处罚不可丢失事实
  -> 130 EAST 可观察事实 <-> 000 资产检索
  -> 140 查询规格
  -> 150 question-SQL 主生成
  -> 160 确定性预审
  -> 170 DeepSeek 独立审核 + 180 GLM 独立审核
  -> 110 路由通过或上游修复
  -> 210 data 阶段调度
  -> 220 结构闭包 <-> 000 资产检索
  -> 230 操作闭包 --+------> 251 ORM -> 252 ORM 验证
                    +------> 241 初始数据 -> 242 数据验证
  -> 260 SQL 回归与根因归类
  -> 210 正式发布候选 -> 010 固定发布
```

Foundation 铺底支路：

```text
用户铺底请求 或 260 发现缺少业务发生前对象/状态
  -> 010 / 210 -> 220 结构闭包 -> 241 候选铺底数据
  -> 242 数据验证 -> 260 铺底回归
  -> 210 正式发布候选 -> 010 固定发布
```

铺底不经过 230、251、252，也不输出“已回归含数据 ORM”；其成功凭据是“铺底回归报告”。

## 5. Question-SQL 阶段

| Agent | 固定职责 | 关键输出与边界 |
|---|---|---|
| `110-question-sql阶段调度agent` | 调度 120 至 180，汇总双审核，按最上游受损产物路由修复。 | 不做开放式语义裁决。 |
| `120-监管处罚不可丢失事实构造agent` | 从处罚原文提取主体、行为、对象、时间、金额、条件、结论和未知项；可检索互联网补充背景/规则。 | 输出监管处罚不可丢失事实包；外部证据不得覆盖处罚原文。 |
| `130-EAST可观察事实构造agent` | 将处罚事实映射到主题、表、字段与关联，并迭代调用 000 验证。 | 证据不足可声明不可观察或人工阻断，不能臆造 EAST 映射。 |
| `140-查询规格agent` | 定义查询对象粒度、入口、路径、筛选、返回字段、正反例、密度与 JOIN 目标。 | 输出查询规格包，是后续生成和审核的共同合同。 |
| `150-Codex question-sql主生成agent` | 基于查询规格生成 question、Gold SQL、SQL 解释、业务事件候选和逐项映射。 | 只能输出待预审结果，不能自批。 |
| `160-确定性预审agent` | 检查 SQL、Schema、类型、引用、固定格式等确定项。 | 不做处罚语义和业务语义裁决。 |
| `170-DeepSeek审核员agent` | 独立审核事实、EAST 映射、查询规格、question-SQL 一致性与业务事件。 | 必须与 180 审同一版本。 |
| `180-GLM审核员agent` | 与 170 独立、并行地执行同范围审核。 | 只输出明确结论、回退分类和可定位的问题说明。 |

生命周期固定为：

```text
待预审question-sql结果包
  -> 待双审核question-sql结果包
  -> 双审核通过question-sql结果包
```

双审核失败时，110 按最早受损环节回退：处罚事实问题回 120，EAST 映射问题回 130，查询规格问题回 140，question/SQL/业务事件表达问题回 150。修复上游包后，旧下游包一律失效并重建。

## 6. Data 阶段：双通路与回归

### 6.1 结构与操作闭包

- `220-结构闭包构造agent`：输入双审核通过的 question-SQL 或 Foundation 铺底任务；多次调用 000，输出表字段范围、相关约束、数据目标与扩张轨迹。它回答“为了满足这条任务，数据世界必须包含什么”。
- `230-操作闭包构造agent`：输入批准的业务事件和结构闭包，输出有序 `READ/CHECK/INSERT/UPDATE` 与事务边界。它回答“业务事件如何在现有状态上执行”。Foundation 不调用它。

### 6.2 数据通路

- `241-初始数据生成与修改agent`：非 Foundation 同时读取结构闭包、230 的同一份操作闭包和正式库只读快照，生成与 ORM 稳定占位符一一对应的“表-字段-数据组”；Foundation 读取 profile、结构闭包、带类型引用图和只读快照，不读操作闭包。它不承担操作顺序或 ORM 逻辑。
- `242-数据验证agent`：调用跨表、表、字段三层硬编码模块。通过后将“待验证表-字段-数据组”转为“待回归表-字段-数据组”；失败返回数据验证报告，由 241 修改。

### 6.3 ORM 通路

- `251-ORM生成与修改agent`：根据结构闭包与操作闭包，生成完整但未绑定实际业务数据的声明式 ORM 调用计划。它必须可导入、可编译、可调用；空数据调用不产生写入或副作用。ORM 本身可包含多种 `INSERT/UPDATE` 操作，不能把“操作类型”误理解成 ORM 包只能选一种类型。
- `252-ORM验证agent`：硬编码检查 AST、允许 API、事务、代码哈希、稳定占位符和与 230 操作闭包一致的顺序，并执行无数据干跑。它不消费独立 ODS 资产。通过后产出“待回归 ORM”；失败由 251 修改。

### 6.4 260 回归与根因路由

`260-SQL回归验证agent` 在内部绑定“待回归 ORM”和“待回归表-字段-数据组”，在沙箱执行并检查 Gold SQL 命中、反例排除、结果密度、分组、`DISTINCT`、JOIN 发散等。内部绑定包不对外成为协议包。

失败时先分析根因，再路由：

| 根因 | 回退目标 |
|---|---|
| 候选数据值错误 | `241` |
| ORM 操作计划错误 | `251` |
| Gold SQL 执行错误 | `010 -> 110 -> 150` |
| 缺少业务发生前已有对象或状态 | `210` 启动 Foundation 铺底 |
| 无法归类或基础设施异常 | 人工审核/运行治理，不得伪装成业务规则错误 |

事件通路通过后输出“已回归含数据 ORM”；Foundation 通路通过后只输出“铺底回归报告”，其中应有待执行的完整、冻结、参数化 INSERT SQL 批次及其哈希、数据库版本和回归结果。

## 7. Agent 分工总表

| 分组 | Agent | 执行边界 |
|---|---|---|
| 公共 | `000-资产检索agent` | LLM 将查询目的转为受限检索计划；硬代码编译参数化只读查询、执行 SQL 安全检查与审计。 |
| 公共 | `010-EAST总体调度agent` | 唯一用户入口、跨阶段回退、Foundation 启动、固定发布。无语义裁决权。 |
| Question-SQL | `110, 120, 130, 140, 150, 160, 170, 180` | 见第 5 节。 |
| Data | `210-data阶段调度agent` | 编排数据阶段与 Foundation，不直接做 LLM 裁决或正式写库。 |
| Data | `220, 230, 241, 251` | 有受控 LLM 思考能力，均只能产生候选或计划。 |
| Data | `242, 252, 260` | 纯硬编码验证/回归，不生成候选数据，不修改 ORM。 |

当前固定分类：需要 LLM 思考能力的是 `000、120、130、140、150、170、180、220、230、241、251`；纯工作流控制的是 `010、110、210`；硬编码审核/验证的是 `160、242、252、260`。

## 8. 包协议与可追溯性

所有跨 Agent 包均继承“产物通用信封”，至少包含：

```text
artifact_id, artifact_type, run_id, qa_id, version, schema_version,
content_hash, supersedes_ref, attempt_no, producer_id, parent_artifact_refs
```

`parent_artifact_refs` 指向上游包的 `artifact_id + version + content_hash`。它表示内容血缘，不是操作系统文件路径，也不要求下游 Agent 去某个目录“找文件”。物理存储路径只是实现细节。

关键包按阶段包括：

- Question-SQL：监管处罚来源包、监管处罚不可丢失事实包、约束资产查询请求/结果、EAST 可观察事实包、查询规格包、三阶段 question-SQL 结果包、DeepSeek/GLM 审核结果包。
- Data：Foundation 铺底任务包、结构闭包、操作闭包、待验证/待回归表-字段-数据组、数据验证报告、待验证/待回归 ORM、ORM 验证报告、SQL 回归验证报告、已回归含数据 ORM、铺底回归报告。
- 发布：正式发布候选包、正式发布回执。

每个包的精确字段、生产者和消费者以 `config/v5-package-catalog.json` 与 `contracts/v5-runtime-packages.schema.json` 为准；历史 V2 Excel 只用于追溯迁移，不得指导实现。

## 9. 000 资产检索与约束资产 V1

000 是公共能力，不是只服务 question-SQL 的检索器。130、220 以及未来的约束模块构建都会调用它。它以结构化查询协议为主，硬代码编译参数化 SQL；受限 NL2SQL 只能作为兜底，且必须限制在白名单视图、`SELECT`、AST 校验、行数、超时和审计范围内。

000 运行期只返回已发布、有效的约束资产；待审、被覆盖、拒绝记录仅供构建审核工具读取。字段命中时，应连带返回相关数据元约束、码表切片和来源引用。组织架构树、科目树等 V1 未发布能力必须明确说明“本版本未发布”，不能静默返回空集。

约束资产 V1 的四类运行期对外资产为：

1. 数据元约束资产：000 可查、结构闭包可包含；不生成数据元模块。
2. 单字段约束资产：以字段为主键，聚合数据元、格式、码值、隐私、检核、答疑等；字段模块未来消费此类资产。
3. 表内多字段约束资产：按表装配，底层仍保留独立规则 ID；表模块未来消费。
4. 跨表多字段约束资产：每条关系约束独立编号；跨表模块未来消费。

历史第 5 类“对象-明细-状态资产”已废止为独立运行期资产：结构/引用事实由正式多字段约束和带类型引用图承接；`READ/CHECK/INSERT/UPDATE` 顺序由 230 操作闭包承接；252 只验证 ORM 与操作闭包一致性。

当前 V1 的主要事实来源是 EAST 原始材料。附件 3 作为 74 表、1963 字段、301 数据元骨架；附件 4 当前检核规则页为检核基线；附件 2 提供默认值、隐私/脱敏及全局数据语义；业务代码表提供正式码表。四期答疑在本轮 V1 暂不进入资产发布，只保留来源清单和延期标记，不能作为覆盖或查询依据。约束资产的详细目标和 SQLite 概念模型见第 1 节所列工作簿。
